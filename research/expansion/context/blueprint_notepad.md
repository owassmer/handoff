- An assessment or accepted account does not create cash movement. A deposit application, refund, return and non-cash adjustment have different effects. Correct recognized entries through linked changes rather than rewrite them.
- A proposed settlement is not a completed agreement/performance. An accounting write-off does not alone extinguish a legal right. Active recovery can conclude under an accepted disposition without falsely erasing every underlying claim.
- Physical completion requires a supported property outcome, not just invoices. Financial completion requires necessary communications and duties performed or an accepted disposition with no remaining work. They need not finish together.
## 5. Recommendations and permissions

Direct edits and contextual conversation update the same coherent proposal. Distinguish a fact correction, an interpretation, a discretionary concession, a work preference and an instruction to act. Selecting a lower deduction must not rewrite an invoice. When intent is precise and consequences computable, use checked calculations without a compulsory model round-trip; broader implications still receive reasoning. Do not build a general simple/complex edit classifier or make the agent an approver of the user's judgment.
A complete recommendation answers the decision needed now. Real operational uncertainty may require an appropriate present treatment and follow-through, including timely interim accounting where applicable. It does not justify waiting mechanically for all repairs or final invoices. Public-source acquisition gaps in demonstration preparation are a separate issue and can be filled coherently.
- Work-plan acceptance binds intended result, scope, budget and explicit requirements. The agent manages other suitable delivery choices. Do not ask the user to classify every field with a fixed/flexible toggle.
- Account acceptance binds the proposed treatment, parties, relevant destinations/instructions and financial follow-through as a coherent package. Do not add a user approval to every underlying operation.
- Only relevant changes require reconsideration. Unrelated messages or ordinary execution adjustments do not invalidate an accepted mandate. Material changes to that mandate or account require the appropriate revised recommendation.
- Bind acceptance to the exact content reviewed. Preserve accepted/issued artifacts. Retain unaccepted versions selectively for a concrete use, not automatically forever or in several duplicate stores.
- Investigation and information requests can occur before acceptance. A binding order or financial promise refers to accepted intent or a genuine standing instruction; free-text email is not an authority bypass.
- Judgment changes are case-specific unless explicitly given continuing scope. Prior decisions can inform reasoning, but repetition alone does not create a new operating rule. Shared fact corrections and later model training are distinct.
- Start with a small workspace capability set—view, work, decide, configure—with User/Admin as access presets rather than professions. Keep access and authority separate from business-party relationships.
- Authorized workspace users share visibility by default, with actual restrictions where needed. Assignment directs attention, not automatic secrecy.
- Enforce identity and permission server-side. The agent can do casework and execute accepted instructions, not fabricate a user's decision or change its own grants. Documents, tool results and caches obey their source/data access scope.

## Minimal execution mechanics

For longer reasoning followed by consequential changes, a candidate pattern is to establish any needed committed claim, perform bounded reasoning, admit the change against current authority/material state, and preserve the external instruction and outcome information needed for recovery. This is not a mandatory four-stage framework. A read-only question, a deterministic edit and a potentially irreversible payment do not automatically need the same machinery.
- Use a single guarded Action where sufficient. Reuse the existing command/recovery mechanisms before introducing infrastructure or extra object families.
- Where separate durable stages are necessary, connect them through committed state and supported sequencing. A resumed invocation is not a suspended JavaScript stack. Standard edit batches do not commit partway through a function; do not depend on beta staged writes for that behavior.
- OSv2 Action edit groups and limited edited-object version checks are not a general serializable multi-object compare-and-swap guarantee. Identify the relevant objects actually guarded/modified and any mutable read-only or absence assumptions. Prove the required behavior with focused tests rather than infer it from a busy flag or sequential replay.
- A new unrelated input should not automatically discard useful reasoning. A stale material basis is reconsidered before consequential action.
- The configured Automation owner is the execution identity. Keep it distinct from the approving user and do not forge user identity.
- Responsiveness is measured behavior: acknowledge promptly, avoid unnecessary scheduling delay and show longer work honestly. Start with one shared coordinator; add a faster wake-up only if needed. Do not create a second interactive agent or another service in advance.
- Ordinary same-person token refresh preserves drafts. Actual identity/access changes invalidate protected client state while retaining only the small recovery references needed to investigate possibly completed requests.
